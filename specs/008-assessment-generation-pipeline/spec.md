# Feature Specification: Assessment Generation Pipeline

**Feature Branch**: `008-assessment-generation-pipeline`

**Created**: 2026-09-01

**Status**: Draft

**Input**: User description: "assessment-generation-pipeline: a staged pipeline (docs/technical-prd.md section 15, roadmap Phase 4) that turns an assessment blueprint (the existing Assessment domain type from Phase 0) into a validated, reusable question-bank entry a student can actually be given. Scope: (1) candidate generation -- an LLM call grounded in the blueprint's target concepts/edges' real confirmed course material, explicitly instructed not to copy source examples verbatim, producing a candidate with question text, rubric/answer key, hints, common mistakes, and source anchors; (2) validation layers exactly per PRD 15.4, run in sequence, each with a specific pass/fail outcome recorded: schema validation, a source-alignment check, an independent solve (deterministic-grading's existing checkers where applicable, otherwise a separate model call solving the question without seeing the candidate's own answer), an answer-agreement check, an ambiguity check, and a similarity check rejecting a near-copy of course homework/practice material; (3) only a candidate that passes every validation layer is persisted into a reusable question bank; a candidate that fails any layer is either regenerated (bounded retry) or rejected outright, never silently published with a known problem; (4) every validation layer's real outcome is retained on the question bank entry for later inspection/audit. Out of scope: presenting a question to a student and grading their real attempt (review-scheduler/practice-session, not yet specified); visual/graph-tree question rendering and vision-based grading (Phase 6); bounded math question generation."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A course owner turns a blueprint into a real, grounded candidate question (Priority: P1)

Given an assessment blueprint (which concepts/edges to target, what kind
of question, how hard, what response format), the system generates one
candidate question — question text, a rubric/answer key, hints, and
common mistakes — grounded in and traceable to the course's own
confirmed material, never copied verbatim from a source example.

**Why this priority**: Every other story in this feature validates or
gates this candidate; without real, grounded generation happening
first, there's nothing for the validation pipeline to check.

**Independent Test**: Submit a blueprint targeting a confirmed concept
with real source material; confirm the generated candidate's claims are
traceable to that material and its question text isn't a verbatim copy
of any single source excerpt.

**Acceptance Scenarios**:

1. **Given** a blueprint targeting concepts/edges with real confirmed
   course material, **When** a candidate is generated, **Then** it
   includes question text, a rubric/answer key, hints, common mistakes,
   and source anchors into that real material.
2. **Given** the same blueprint, **When** a candidate is generated,
   **Then** its question text is not a verbatim copy of any single
   source excerpt it's grounded in.
3. **Given** a blueprint whose target concepts have little or no real
   source material to ground a question in, **When** generation is
   attempted, **Then** the system reports that plainly rather than
   fabricating a plausible-sounding but ungrounded question.

---

### User Story 2 - A candidate question is proven correct before it's reusable (Priority: P1)

Before a candidate reaches the reusable question bank, it passes every
validation layer in sequence — schema, source-alignment, an independent
solve, answer agreement, an ambiguity check, and a similarity check —
and every layer's real outcome is recorded, not just an overall
pass/fail. A candidate that fails any layer is regenerated (bounded) or
rejected; it never reaches the bank with a known, unresolved problem.

**Why this priority**: This is the trust guarantee the entire feature
exists to provide — a generated question a student is actually given
must be provably correct, not merely "generated by a capable model."
This is exactly this project's own core differentiator applied to
question generation itself.

**Independent Test**: Run a well-formed candidate through the full
validation sequence and confirm it passes every layer and reaches the
bank with each layer's outcome recorded; run a candidate with a
deliberately wrong answer key and confirm it fails the independent-solve/
answer-agreement layers and never reaches the bank.

**Acceptance Scenarios**:

1. **Given** a generated candidate, **When** it's validated, **Then**
   each of the six validation layers runs in sequence and its specific
   outcome (not just an aggregate boolean) is recorded.
2. **Given** a candidate whose stated answer key disagrees with an
   independent solve of the same question, **When** validated, **Then**
   the answer-agreement layer fails and the candidate does not reach
   the question bank.
3. **Given** a candidate targeting a domain `deterministic-grading`
   already has a checker for, **When** the independent-solve layer
   runs, **Then** it reuses that existing checker rather than a second
   model call solving the same kind of problem.
4. **Given** a candidate that fails a validation layer, **When** the
   pipeline handles the failure, **Then** it either regenerates a new
   candidate (up to a bounded number of attempts) or rejects it
   outright — it is never published to the question bank with the
   known problem unresolved.
5. **Given** a candidate that passes every layer, **When** it's
   persisted, **Then** the question bank entry retains every layer's
   real recorded outcome, inspectable later, not just the final
   pass/fail.

---

### User Story 3 - A genuinely ambiguous question is caught before it reaches a student (Priority: P2)

A dedicated reviewer check asks specifically whether a candidate has
more than one reasonable interpretation or correct answer. A candidate
flagged as ambiguous does not reach the question bank as-is.

**Why this priority**: An ambiguous question is a distinct failure mode
from a wrong answer key — the question itself is the problem, not the
stated answer — and this project's own design already treats "the
question is malformed" as different from "the answer is wrong"
(mirroring `deterministic-grading`'s own `invalid_input` outcome). Lower
priority than Story 2 because it's a narrower, less frequent failure
mode than a flatly incorrect answer key.

**Independent Test**: Run a candidate with a genuinely ambiguous
question (more than one reasonable correct answer given the blueprint's
constraints) through the ambiguity check and confirm it's flagged and
does not reach the bank as-is.

**Acceptance Scenarios**:

1. **Given** a candidate with only one reasonable interpretation and
   answer, **When** the ambiguity check runs, **Then** it passes.
2. **Given** a candidate with more than one reasonable interpretation or
   correct answer given its own stated constraints, **When** the
   ambiguity check runs, **Then** it's flagged as ambiguous and the
   candidate does not reach the question bank as-is.

---

### User Story 4 - A near-copy of real homework/practice material never enters the bank (Priority: P2)

A candidate that's too similar to the course's own uploaded homework or
practice material is rejected, protecting against a generated "new"
question that's really just a lightly-reworded copy of material
students may already have seen the answer to.

**Why this priority**: A near-copy defeats the point of generating
*new* practice — a student who's seen the homework answer isn't being
tested on their own understanding. Lower priority than Stories 1-2
since it's a narrower check applied after a candidate is otherwise
already sound.

**Independent Test**: Run a candidate that closely mirrors a real
uploaded homework/practice question through the similarity check and
confirm it's rejected; run a genuinely original candidate on the same
underlying concept and confirm it passes.

**Acceptance Scenarios**:

1. **Given** a candidate that's a near-copy of the course's own
   uploaded homework/practice material, **When** the similarity check
   runs, **Then** it fails and the candidate does not reach the
   question bank.
2. **Given** a candidate covering the same concept but genuinely
   distinct from any specific source question, **When** the similarity
   check runs, **Then** it passes.

---

### Edge Cases

- What happens when a blueprint's target concepts/edges don't actually
  exist (were never confirmed, or were archived)? Generation must fail
  plainly, not proceed against nonexistent targets.
- What happens when every regeneration attempt for a candidate still
  fails validation? The blueprint's request is reported as
  unfulfilled — never silently downgraded to publishing the
  best-of-a-bad-lot failing candidate anyway.
- What happens when the independent-solve layer itself can't produce a
  confident answer (e.g. the underlying deterministic checker reports
  the *question's own* structured input as malformed)? That's treated
  as a validation failure of the candidate, not a system error to
  ignore — the candidate that produced malformed checker input is
  itself the problem.
- What happens when a candidate's blueprint requires prerequisites the
  course doesn't confirm exist yet? Generation must fail plainly (same
  as a nonexistent target concept) rather than fabricating a
  prerequisite relationship that was never actually confirmed.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Given a blueprint targeting real confirmed course
  concepts/edges, the system MUST generate a candidate question
  grounded in and traceable to that course's own real, confirmed
  material.
- **FR-002**: A generated candidate MUST include question text, a
  rubric/answer key, hints, common mistakes, and source anchors into
  real course material.
- **FR-003**: A generated candidate's question text MUST NOT be a
  verbatim copy of any single source excerpt it's grounded in.
- **FR-004**: A blueprint targeting concepts/edges with no real
  confirmed course material to ground a question in MUST fail plainly,
  never produce a fabricated, ungrounded candidate.
- **FR-005**: Every candidate MUST pass, in sequence, all of: schema
  validation, a source-alignment check, an independent solve, an
  answer-agreement check, an ambiguity check, and a similarity check
  before it may be persisted to the question bank.
- **FR-006**: Each validation layer's real, specific outcome MUST be
  recorded — never collapsed into a single aggregate pass/fail with no
  detail on which layer produced it or why.
- **FR-007**: The independent-solve layer MUST reuse an existing
  deterministic checker when the candidate's response modality is a
  domain one already exists for, rather than a second model call
  re-solving a problem an exact checker can already verify.
- **FR-008**: A candidate failing any validation layer MUST be either
  regenerated (up to a bounded number of attempts) or rejected — it
  MUST NOT be persisted to the question bank with a known, unresolved
  validation failure.
- **FR-009**: A candidate flagged ambiguous by the ambiguity check MUST
  NOT reach the question bank as-is.
- **FR-010**: A candidate that's a near-copy of the course's own
  uploaded homework/practice material MUST be rejected by the
  similarity check.
- **FR-011**: A question bank entry MUST retain every validation
  layer's real recorded outcome, inspectable after the fact, not just
  the final accept/reject decision.
- **FR-012**: A blueprint whose target concepts/edges/prerequisites
  don't actually exist as confirmed course material MUST fail
  generation plainly, never proceed against a target that doesn't
  really exist.

### Key Entities

- **Assessment Blueprint**: The existing specification for what
  question to generate (target concepts/edges, assessment type,
  difficulty, style references, required prerequisites, forbidden
  concepts, response modality, expected solution properties, max time)
  — this feature consumes it, it doesn't redefine it.
- **Candidate Question**: One generated attempt at fulfilling a
  blueprint — question text, rubric/answer key, hints, common mistakes,
  source anchors — not yet validated, not yet reusable.
- **Validation Report**: The real, specific outcome of each of the six
  validation layers for one candidate, retained regardless of whether
  the candidate ultimately passed or failed.
- **Question Bank Entry**: A candidate that passed every validation
  layer, persisted as reusable, together with its full validation
  report.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of question bank entries have every validation
  layer's real outcome recorded and inspectable — none are persisted
  with unknown or unrecorded validation status.
- **SC-002**: 0% of question bank entries have a stated answer key that
  disagrees with an independent solve of the same question performed
  during validation.
- **SC-003**: 0% of question bank entries are flagged ambiguous by
  their own recorded ambiguity-check outcome.
- **SC-004**: 0% of question bank entries are near-copies of the
  course's own uploaded homework/practice material, per their own
  recorded similarity-check outcome.
- **SC-005**: For blueprints targeting concepts/edges with real
  confirmed course material, generation produces a validated question
  bank entry (directly or after bounded regeneration) at least 70% of
  the time — a starting target, not a fixed permanent bar (Assumptions).
- **SC-006**: 100% of candidates targeting a blueprint whose concepts/
  edges/prerequisites don't actually exist fail generation plainly,
  with zero fabricated candidates produced against nonexistent targets.

## Assumptions

- This feature reuses `deterministic-grading`'s existing checkers for
  the independent-solve layer wherever the blueprint's response
  modality matches a domain those checkers already cover — it does not
  reimplement or duplicate that checking logic.
- This feature reuses `course-graph-ingestion`'s existing confirmed
  concepts/edges (and their source anchors) as the grounding material
  for generation — it does not introduce a second, parallel course-content
  retrieval mechanism.
- "Course homework/practice material" for the similarity check refers
  to the same uploaded artifacts `course-graph-ingestion` already
  processes — no new upload/content-type is introduced by this feature.
- The bounded number of regeneration attempts before a blueprint's
  request is reported as unfulfilled is a tunable starting parameter,
  not a fixed, precisely-calibrated number from day one — same
  treatment as every other tunable threshold already established in
  this project (`learner-graph-evidence`'s weights,
  `tutor-agent`'s ladder, `deterministic-grading`'s confidence
  threshold).
- SC-005's 70% generation-success target is a starting assumption to
  measure against, not a contractual guarantee — consistent with how
  this project has already treated its own extraction-quality numbers
  (`course-graph-ingestion`'s recorded recall/precision) as an honest
  baseline to improve on, not a number to hit by construction.
- "Student" and course owner remain the same account for now, matching
  every other feature's current scope in this project — no separate
  enrollment model exists yet, and no student-facing question-delivery
  UI is in scope here (Out of Scope).
